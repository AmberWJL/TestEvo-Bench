TestEvo-Bench

a benchmark of co-evolving test / production pairs
drawn from real open-source Java projects

Code Dataset

Abstract

In real software, tests and the production code they exercise are written and revised together; a change to a production method almost always arrives with a coordinated change to its test. Existing benchmarks for test generation and test update evaluate the two sides in isolation, which discards this co-evolution signal and makes it hard to tell whether a model actually understands how a change should propagate from implementation to test. We introduce TestEvo-Bench, a live, continuously ingested benchmark of co-evolving test/production pairs mined from the public commit histories of real open-source Java projects. Each task is anchored to a concrete rev-pair in which a production edit is accompanied by a contemporaneous edit to the associated test suite, preserving the temporal and semantic link between the two artefacts. TestEvo-Bench ships two evaluation tracks. In test update, a model must revise an existing test so that it still compiles, exercises the new behaviour of the modified production method, and passes — without weakening assertions or deleting coverage. In test generation, the model must write a brand-new test for newly added or updated production code that compiles, runs, passes, and meaningfully covers the changed lines. Because tasks are ingested from live commit streams rather than fixed at release time, TestEvo-Bench enables contamination-aware evaluation: a time filter restricts tasks to any chosen rev2 date window, so results can be reported strictly against commits authored after a model's pre-training cutoff. We release the benchmark together with an open leaderboard that tracks compile pass rate, test pass rate, line and mutation coverage, and — for test update — the coverage delta on lines that were actually changed.

Track 1 — Test Update

Production code changes; the paired test must be updated to compile, exercise the new behavior, and pass. Example from gazbert/bxbot v1.4.0.
production BotStatus.java
@Override
public String toString() {
return MoreObjects.toStringHelper(this)
.add("botId", botId)
.add("displayName", displayName)
.add("status", status)
.add("datetime", getDatetime())
.toString();
}
test update TestBotStatus.java
@Test
public void testToStringWorksAsExpected() {
final BotStatus botStatus = new BotStatus(BOT_ID, DISPLAY_NAME, STATUS);
assertEquals(
"BotStatus{botId=avro-707_1, displayName=Avro 707, status=running}", botStatus.toString());
final BotStatus botStatus = new BotStatus(BOT_ID, DISPLAY_NAME, STATUS, DATE);
assertTrue(botStatus.toString().startsWith(
"BotStatus{botId=avro-707_1, displayName=Avro 707, status=running, datetime="));
}

Track 2 — Test Generation

Production code changes; a new test must be written to compile, exercise the change, and pass. Example from casbin/jcasbin v1.99.0.
production Util.java
public static boolean hasEval(String exp) {
return evalReg.matcher(exp).matches();
return evalReg.matcher(exp).find();
}
test generation UtilTest.java
@Test
public void testReplaceEval() {
Util.logPrint(Util.replaceEval("eval(test)", "testEval"));
}
@Test
public void testHasEval() {
assertTrue(hasEval("eval(test)"));
assertTrue(hasEval("r_act == p_act && eval(p_sub_rule) && eval(p_obj_rule)"));
assertFalse(hasEval("evaltest"));
}

License check failed

The collect-repo stage validates that each repository carries a permissive open-source license (Apache 2.0 or MIT). Repositories with other licences are dropped before any build is attempted.

BaseXdb / basex collect_repo BSD 3-Clause license — not in allowed set 
license=BSD 3-Clause "New" or "Revised" License

The pipeline accepts only Apache-2.0 and MIT licensed repositories. BaseX carries a BSD 3-Clause license, so it was dropped at collection time before any Maven build was run.

openmrs / openmrs-core collect_repo Unrecognised license ("Other") 
license=Other

GitHub classifies this repository's license as "Other" — a custom or composite license that cannot be automatically verified as permissive. The pipeline rejects such repositories to avoid redistribution ambiguity.

No qualifying commits

After cloning, the pipeline scans the Git history for commits that touch Java source files. Repositories with no such commits are abandoned early.

apache / commons-math commit_extraction No commits with Java file changes found 
No commits with Java file changes found in repository

The scanned branch of commons-math contained no commits in which a .java source file was modified. This typically occurs when a repository has been migrated or the branch is a documentation/release branch with no source commits in the analysed window.

Maven dependency resolution failure

Multi-module Maven projects where a sibling module hasn't been installed in the local repository, or where a dependency is only available via a now-unreachable HTTP mirror, fail during the collect-repo build step.

The springside-core module depends on springside-utils from the same multi-module project, but that sibling jar was never installed into the local Maven repository. The build environment uses an offline or partially-warm Maven cache, so the artifact cannot be resolved.

JDK version mismatch

Some projects enforce a minimum JDK version via the Maven Enforcer plugin, or use a compiler target release higher than the available JDK. The build environment provides JDK 8, 11, and 17; projects requiring JDK 21 or enforcing a range that excludes the available version fail here.

google / gson mvn_test_compile Enforcer requires JDK 17–22; available JDK is 11.0.23 
[ERROR] Rule 1: org.apache.maven.enforcer.rules.version.RequireJavaVersion failed:
[ERROR] Detected JDK /…/jdk-11.0.23 is version 11.0.23 which is not in the allowed range [17,22).
[INFO] BUILD FAILURE — Total time: 0.840 s

Gson 2.13.x requires at least JDK 17 (and below 22) as declared in its Enforcer configuration. The pipeline selected JDK 11 for this project, causing an immediate Enforcer failure before any sources were compiled.

prebid / prebid-server-java mvn_test_compile Compiler target 21 not supported by available JDK 
[ERROR] Failed to execute goal maven-compiler-plugin:3.14.1:compile:
[ERROR]   Fatal error compiling: error: invalid target release: 21
[INFO] BUILD FAILURE — Total time: 38.759 s

The project's pom.xml sets <maven.compiler.target>21</maven.compiler.target>. The JDK available to the build does not support Java 21 bytecode, so javac rejects the target release. 2002 source files were processed before the error was detected.

Test compilation failure

A project may compile its main sources successfully but fail to compile its test sources when a test-scope dependency was itself compiled for a newer JDK.

[WARNING] Can't extract module name from equalsverifier-4.0.jar: Unsupported major.minor version 61.0
[ERROR] COMPILATION ERROR:
[ERROR] CrosshairTest.java:[46,30] cannot access nl.jqno.equalsverifier.EqualsVerifier
  bad class file: equalsverifier-4.0.jar(…/EqualsVerifier.class)

Java class file version 61.0 corresponds to Java 17; version 55.0 corresponds to Java 11. equalsverifier 4.0 was compiled with JDK 17 but JFreeChart's test classpath is built against Java 11 release mode, creating an incompatible class-file version error in CrosshairTest.

Apache RAT license audit failure

Apache Commons projects run the Apache RAT (Release Audit Tool) plugin during the build to verify that every file carries an approved license header. RAT flags any file without a recognised header, causing a build failure even though all Java sources compile and tests pass.

apache / commons-collections jacoco_coverage RAT found 1 unapproved file: class_path.txt 
[ERROR] Unexpected count for UNAPPROVED, limit is [0,0]. Count: 1
Files with unapproved licenses:
  /class_path.txt
[ERROR] Failed to execute goal apache-rat-plugin:0.17:check (rat-check):
        Counter(s) UNAPPROVED exceeded minimum or maximum values.
[INFO] BUILD FAILURE — Total time: 9.755 s

The JaCoCo agent writes a class_path.txt helper file that does not include an Apache license header. RAT treats this as an unapproved file and fails the build. The issue is an interaction between the JaCoCo instrumentation step and the RAT audit, not a problem with the project's own sources.

apache / commons-lang jacoco_coverage RAT found 1 unapproved file: class_path.txt 
[ERROR] Unexpected count for UNAPPROVED, limit is [0,0]. Count: 1
Files with unapproved licenses:
  /class_path.txt
[ERROR] Failed to execute goal apache-rat-plugin:0.17:check (rat-check):
        Counter(s) UNAPPROVED exceeded minimum or maximum values.
[INFO] BUILD FAILURE — Total time: 11.263 s

Same root cause as commons-collections: the JaCoCo agent deposits a class_path.txt file at the repo root, which the RAT plugin then flags as lacking a license header.

Test runtime failure

These repositories compile cleanly and most tests pass, but one or more test cases fail at runtime due to missing cryptographic algorithms or timing-sensitive assertions.

apache / commons-codec jacoco_coverage JDK missing SHA-512/224 and SHA-512/256 MessageDigest providers 
[ERROR] Errors:
[ERROR]   DigestUtilsTest.testGetDigests:435 » IllegalArgument
          java.security.NoSuchAlgorithmException: SHA-512/224 MessageDigest not available
[ERROR]   DigestUtilsTest.testSha512_224:801 » IllegalArgument
          java.security.NoSuchAlgorithmException: SHA-512/224 MessageDigest not available
[ERROR]   DigestUtilsTest.testSha512_256:821 » IllegalArgument
          java.security.NoSuchAlgorithmException: SHA-512/256 MessageDigest not available
[ERROR] Tests run: 19015, Failures: 0, Errors: 3, Skipped: 74
[INFO] BUILD FAILURE — Total time: 49.621 s

SHA-512/224 and SHA-512/256 are truncated variants of SHA-512 defined in FIPS 180-4. They were added to the standard JDK security providers only in JDK 17. The build environment ran this project under an older JDK that does not include these providers, causing three DigestUtilsTest cases to throw NoSuchAlgorithmException.

The test asserts that a cache entry is still present after a background cleanup sweep, but the cleanup task ran and evicted the entry before the assertion was reached. Build timeout

The pipeline enforces a hard 1800-second (30-minute) wall-clock limit on mvn test. Very large monorepos with heavyweight integration tests can exceed this limit.

apache / rocketmq jacoco_coverage mvn test timed out after 1800 s; broker cluster tests deadlocked on metadata 
jacoco `mvn test` timed out after 1800s

… (27 000+ lines of test output) …

ERROR [RocketmqBroker] Register to broker failed 5 times
ERROR [RocketmqBroker] Failed to start replicasManager
ERROR [RocketmqBroker] fail to apply broker id: 1
ERROR [RocketmqBroker] The clusterName: default-cluster in broker metadata is different
                        from the clusterName: default-cluster1 in broker config
ERROR [RocketmqBroker] Check and find that metadata/tempMetadata invalid

… (broker registration retry loop repeated hundreds of times) …

Caused by: org.apache.rocketmq.filter.parser.ParseException:
  Encountered " <ID> "x "" at line 1, column 16. Was expecting: <STRING_LITERAL>

RocketMQ's broker integration tests spin up an in-process broker cluster. Several tests entered a retry loop when the broker could not register with the controller (mismatched clusterName in metadata vs. config), consuming the full 1800-second budget before the Maven Surefire plugin could terminate them. Additionally, ExpressionTest exposed a parser failure when non-string literals appear in selector positions.

Silent instrumentation failure

Code instrumentation (bytecode rewriting to track which lines are executed) is a prerequisite for collecting coverage data. A silent failure — no stdout, no stderr — indicates the instrumentation process crashed or was killed before producing any output.

apache / shenyu instrumentation Instrumentation produced no output — process exited silently 
=== STDOUT ===
(empty)

=== STDERR ===
(empty)

The instrumentation worker for apache/shenyu produced neither standard output nor standard error. The most common causes are an out-of-memory crash before any logging could occur, a JVM abort signal, or the container being killed by the OS due to resource exhaustion. Without any log output the precise cause cannot be determined from this artefact alone.
